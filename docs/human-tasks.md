# sapiens 人工工单接入微信

IM 使用 runtime 公开的 `human_task.*` CLI 能力读取工单、登记微信投递、转述人的回执；不直接写 runtime 工单文件，也不让语言模型替人完成工单。支持从终端、后台 worker 或微信启动的 sapiens 会话。

## 配置和启动

需要支持 `human_task.*` 的外部 runtime（建议 >= 0.12.1）。IM 和 runtime 必须使用相同系统用户及 `META_AGENT_HOME`。

单人使用无需配置 `userId` 或路由文件。在 `.env` 开启：

```dotenv
META_AGENT_HUMAN_ENABLED=true
```

重启机器人后，给它私聊发任意一条消息，程序会自动保存你的机器人账号、微信用户 ID 和会话 token，并把你作为唯一工单收件人。以后重启会继续沿用，不会因后来的其他消息改绑。升级时若已有唯一可用的私聊记录，会直接沿用；首次绑定之前的工单保留待投递，绑定后补发。群消息和不符合 `WEIXIN_ALLOW_FROM` 的消息不会触发绑定。

所有项目的新工单都会默认通知你，包括带 `assigneeRole` 的工单，以及从终端或后台 worker 发起、没有微信会话归属的工单。人工回填模式中的 `whoami` 仅用于查看当前微信身份，无需用它取 ID 再填写配置。

可选配置：`META_AGENT_HUMAN_BIN` 指向有执行权限的 runtime CLI，未设置时沿用 `META_AGENT_TASKS_BIN`，否则用 `meta-agent-glm`；`META_AGENT_HUMAN_POLL_MS` 默认 5000 毫秒。CLI 参数通过数组传递，不使用 shell。原有 `WEIXIN_ALLOW_FROM` 白名单继续生效。

旧版手工配置的默认收件人（`META_AGENT_HUMAN_DEFAULT_USER_ID` / `META_AGENT_HUMAN_DEFAULT_ACCOUNT_ID`）和项目路由（`META_AGENT_HUMAN_ROUTES`）仍兼容；存在手工配置时沿用它们。采用自动识别时删除这些旧配置即可。已发送工单仍锁定原接收人。

```sh
npm run agent:human-check  # 只读检查后端及路由；不连接微信、不调用模型
npm run agent
```

自检会显示自动识别到的收件人（尚未绑定时提示先私聊）并查询待办，因此 runtime 可能按其惰性过期规则把超期工单标记为 expired。自检不验证微信 token，也不代表调度器已启动。正常启动时由后台轮询探测后端，查询或投递失败会记录日志并重试，不会阻止微信开始监听。聊天、运维模式和身份查询不会等待后台投递队列；工单回填操作按序执行。

## 微信操作

- 单独发送 `/auto`，再发送 `--sapiens <目标>` 创建人工协作任务；`auto/` 退出工作模式。
- 单独发送 `/human` 进入人工回填模式，随后直接发送以下内容。
- `help` 或 `查看工单`：列出自己的未完成工单。
- `H1`：选择该工单上下文并恢复草稿，也支持完整 `ht-…` 编号；已结束工单只显示详情。
- `H1 接单`：接单，不等于完成。
- `H1 填写`：逐项填写字段；支持是/否、数字、文本、枚举以及附件。
- 逐条回复字段值；文件字段直接发送文件、图片或视频。
- `提交`：确认提交；`重填`：重新填写；`退出填写`：保留草稿。
- `H1 拒绝 场地不安全`：带原因拒绝，交由 agent 重新规划。
- `human/`：退出人工回填模式，草稿保留，下次进入后重新选择 H1 等工单即可继续。

工单只在私聊处理，按机器人账号和发送者共同鉴权。Agent 忙碌时仍可回填。模式内内容作为当前字段答案，切换到其他模式必须先退出；一次只填写一张工单，切换工单后原草稿保留。

## 调度续跑

IM 不另起调度器，不通过回执强制运行 parallel 会话。需要按 runtime 的部署方式运行工作区调度器，例如：

```sh
meta-agent-glm -w /home/operator/robot-project auto-scheduler
```

也可使用 runtime 的 `tasks --manage`。回执后 IM 查询 `task.inspect`：只有观察到 running 才提示当前运行中，否则提示“已提交，等待调度”。当前微信 `/tasks` 执行器采用显式准入，不会因提交回执而自动调度所有任务；可用 `/tasks` 查询和显式调度。

## 重启与投递语义

状态位于微信状态目录下 `human/human-tasks.json`，0600 权限，包含自动绑定的收件人、事件游标、待投递队列、账号用户 token、会话归属和草稿。损坏的 JSON 会阻止启动，避免静默丢失投递记录。锁文件防止同一状态目录有多个消费者。

启动及每分钟通过分页待办快照补查，平时增量消费全机事件，每批最多投递十张工单。发送失败指数退避，最长五分钟；新入站消息刷新 token 后可提前重试。成功发消息后立即持久化，再登记 `deliver`；登记失败只重试登记。所有写入重试保留相同 requestId 和参数。

微信发送和本地落盘没有共同事务：发送成功、落盘前崩溃仍可能重复通知；分段消息中途失败也可能重发前面的段落。不承诺 exactly-once。请勿让多个不同状态目录的 IM 实例消费同一组收件人。

取消和过期会通知已接收人停止执行；不会给已结束工单补发派单通知。接收人没有 token 或 token 被服务端拒绝时，保留待投递和错误日志，待其再次私聊刷新。持久化 token 不保证长期有效，实际投递受微信服务端约束。

提交时若响应丢失，IM 先读取实际回执，核对发送者、渠道、消息 ID、转述应用、结果及原始回复。当前 runtime 的人工工单写入虽接受 requestId，但并不全部支持终态重放，因此不能仅依赖重试返回成功。无法核验时草稿保留不可变的原提交；再次回复“提交”重试，不能“重填”绕开未知结果。明确的字段校验失败可重填。工单记录、草稿及附件缓存的清理目前由运维管理，不自动删除用户资料。

开发验证：`npm test` 运行模拟测试；`IM_TEST_RUNTIME_DIR=/absolute/path/to/meta_agent_runtime node --test test/human-tasks-runtime.test.mjs` 使用本地已构建 runtime 在临时目录验证真实 CLI、附件入库及响应丢失后的核验，不发送真实微信消息、不调用模型。
